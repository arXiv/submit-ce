# SUBMISSION-257 — Submission Mutation API (Phase 1 plan)

A FastAPI service in submit-ce that lets other services (starting with
arxiv-check) mutate submissions through the Submit 2.0 event model
(`SubmitApi.save()`), never by writing the DB directly, so every change inherits
the event log and the `SELECT ... FOR UPDATE` critical section. Full discovery:
[`docs/submission-mutation-api-discovery.md`](../../submission-mutation-api-discovery.md).

## Endpoints (named verbs, bearer JWT auth)

- `POST /submission/{id}/resubmit` → `CreateSubmissionVersion` (announced → new
  working `rep` version). Reuses an existing event.
- `POST /submission/{id}/remove` → **new `AdminRemove`** → `REMOVED` (classic 9).
  The admin/moderator remove arxiv-check uses today. Reversible. Optional
  `comment` is written to the classic admin log.
- `POST /submission/{id}/unremove` → **new `UnRemove`** → removed → on hold
  (`SUBMITTED` + a hold, classic 2), matching legacy's 9→2. Optional `comment`
  is written to the classic admin log.
- `GET /submission/{id}`, `GET /submission/{id}/with_history` — reads.

Named verbs (not a generic events `PATCH`) so each action carries its own auth
scope and is self-documenting; PATCH is used nowhere else in submit-ce.

## Domain / persistence changes

- `domain/submission.py`: add `REMOVED = 'removed'` status + `is_removed`;
  exclude `REMOVED` from `is_active` (a removed submission is not active).
- `domain/event/__init__.py`: `AdminRemove` (project → `REMOVED`; validate: not
  announced/deleted/already-removed) and `UnRemove` (project → `SUBMITTED` + a
  `PATCH` hold; validate: must be removed).
- `implementations/legacy_implementation/models.py`:
  - `update_from_submission`: `is_removed` → classic `REMOVED` (9), ordered
    first so remove wins over the other predicates.
  - `status_from_classic`: classic `REMOVED` (9) → domain `'removed'` (load side,
    used by `db.py`), so a removed row round-trips.
  - `is_on_hold` already maps to classic `ON_HOLD` (2), so unremove lands on 2.
- `implementations/legacy_implementation/log.py`: `AdminRemove`/`UnRemove` write
  an `arXiv_admin_log` row (with the optional comment) via the existing
  `ON_EVENT` dispatch — audit-trail parity with legacy/modapi.

## Terminology (kept distinct on purpose)

remove (admin, status 9) ≠ delete (user, `Rollback` → 10) ≠ withdraw (new `wdr`
version) ≠ rollback (2.0 unannounced delete). resubmit here = submitter replace.

## Tests

- `domain/event/tests/test_admin_remove_unremove.py` — event projection +
  validation (remove sets REMOVED / rejects announced+already-removed; unremove
  sets SUBMITTED+on-hold / rejects when not removed; round-trip).
- `implementations/legacy_implementation/tests/test_remove_status_mapping.py` —
  `status_from_classic` maps 9 → 'removed'.
- `fastapi/tests/test_app_wiring.py`, `.../test_routes.py` — app builds, routes
  registered, endpoints dispatch the right event, auth required (401), and the
  optional comment is passed through to the event.

Save-side round-trip (`tests/test_remove_roundtrip.py`): create a submission,
remove → assert classic `arXiv_submissions.status` == 9, unremove → assert == 2,
and assert each writes an `arXiv_admin_log` row carrying the comment (same
no-Flask sqlite setup as `test_fastapi_impl`).
